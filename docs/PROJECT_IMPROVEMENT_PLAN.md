# X-JVM 对标 JDK17 全栈开发路线图（2026-2028）

## 1. 目标与范围

本路线图以 **JDK17 语义与工程能力**为参考，覆盖你要求的核心方向：

- 锁升级与并发原语（含 CAS）
- 多线程执行模型
- 垃圾回收体系（先 G1，再演进到 ZGC 风格并发收集）
- 异常机制完整性
- JVMTI 观测与调试接口
- 工程化（测试、CI、可观测、性能基线）

说明：本项目当前是学习型 JVM，建议采用“**分层对标、逐步逼近**”策略，而不是一次性追齐 HotSpot 全量实现。目标是先把架构和关键语义做对，再做性能和高级优化。

---

## 2. 总体架构蓝图（目标态）

### 2.1 运行时分层

1. **Execution Engine**
   - 解释器（现有）+ 可选模板解释优化
   - 线程调度、栈帧切换、safepoint 协议

2. **Concurrency Runtime**
   - 原子操作抽象层（CAS、fence、原子计数）
   - Monitor/ObjectLock（偏向锁不做，直接轻量锁 + 膨胀锁）
   - Thread 状态机与阻塞原语

3. **GC Runtime**
   - 统一 GC 接口（`IGarbageCollector`）
   - 分代/Region 元数据
   - 写屏障、读屏障（按算法需要逐步引入）

4. **Serviceability**
   - JVMTI 事件、对象/线程探针
   - 诊断日志、profiling hooks、崩溃上下文

5. **Compatibility Layer**
   - ClassFile/字节码语义对齐 JDK17 子集
   - 异常模型与标准错误传播

## 3. 分阶段路线（24 个月建议）

## Phase 0（0-2 个月）：基线加固

### 目标
先把“可验证、可迭代”基础打牢，避免后续并发与 GC 改造在沙地上施工。

### 关键任务

- 消灭核心路径 `exit(1)`，统一错误传播（异常对象或 error code）。
- 核心模块 RAII 化（`unique_ptr/shared_ptr` + 所有权边界文档）。
- 增加 sanitizer（ASan/UBSan/TSan 可选）和覆盖率统计。
- 建立多平台 CI（Linux/Windows 起步，后续加 macOS）。

### 退出标准

- 主链路无硬退出；测试可稳定跑通；
- sanitizer 抽检通过；
- PR 具备构建+测试门禁。

---

## Phase 1（2-5 个月）：并发原语与线程模型（CAS + 多线程 MVP）

### 目标
构建 JVM 级并发地基：可安全扩展到 GC 和锁优化。

### 关键任务

1. **CAS/原子抽象层**
   - 新增 `runtime/concurrent/AtomicOps.h`，统一封装：
     - `compareAndSwap32/64`
     - `fetchAdd`
     - acquire/release/full fence
   - 底层先基于 C++ `std::atomic`，平台相关优化后置。

2. **线程状态机**
   - 状态：`NEW/RUNNABLE/BLOCKED/WAITING/TIMED_WAITING/TERMINATED/AT_SAFEPOINT`
   - 每个 JavaThread 维护 state、interrupted 标记、park/unpark 支持。

3. **Safepoint 协调器**
   - 去掉当前硬编码计数；
   - 支持线程注册/注销；
   - 可暂停全部 mutator 并恢复。

4. **线程调度 MVP**
   - 先“多 Java 线程 + 单解释循环切片调度”（协作式）；
   - 后续再演进到多 OS 线程并行解释执行。

### 退出标准

- CAS 原语有单元测试与并发压力测试；
- safepoint 在多线程下无死锁；
- 线程状态转移符合预期。

---

## Phase 2（5-8 个月）：锁子系统（轻量锁 -> 重量锁）

### 目标
完成 Java 对象监视器（monitor）语义闭环。

### 关键任务

1. **对象头与锁字（Mark Word）简化设计**
   - 不做偏向锁；
   - 先实现：无锁 -> 轻量锁（CAS）-> 膨胀为重量锁（Monitor）。

2. **Monitor 实现**
   - owner、entry list、wait set；
   - `monitorenter/monitorexit` 指令语义落地；
   - `wait/notify/notifyAll` 基础支持。

3. **锁竞争路径**
   - 自旋阈值 + 阻塞回退；
   - 避免长时间忙等。

### 退出标准

- 锁重入正确；
- wait/notify 行为可通过兼容用例；
- 压测下无明显死锁/活锁。

---

## Phase 3（8-12 个月）：异常体系全面化

### 目标
实现 JVM 异常分派与栈展开核心语义，建立“可诊断异常”能力。

### 关键任务

1. **异常表与分派**
   - 解析并使用 method exception table；
   - 支持按 pc 区间与类型匹配 handler。

2. **栈展开与 finally 语义**
   - 异常穿透栈帧时执行必要清理；
   - 统一未捕获异常出口。

3. **标准运行时异常路径**
   - `NullPointerException`、`ArrayIndexOutOfBoundsException` 等核心异常。

4. **异常可观测**
   - 栈轨迹格式化；
   - 错误码与日志上下文统一。

### 退出标准

- 异常路径测试覆盖核心场景；
- 异常时无资源泄漏/状态损坏；
- 错误信息可用于定位问题。

---

## Phase 4（12-16 个月）：G1 风格 GC（优先主线）

### 目标
从当前空 GC 框架演进到“可工作的分区化、分代化、可暂停控制”的 G1 简化实现。

### 关键任务

1. **堆分区（Region）**
   - 统一 Region 元数据；
   - Eden/Survivor/Old 逻辑分层。

2. **Card Table + 写屏障**
   - 支持跨代引用记录；
   - 为并发标记打基础。

3. **标记-整理/复制混合策略**
   - 年轻代优先回收；
   - 老年代按回收收益选择 region。

4. **暂停目标**
   - 建立 pause time 统计；
   - 支持“近似目标暂停时间”策略（先简化）。

### 退出标准

- 可稳定运行中等对象分配压力测试；
- Full GC 触发率明显下降；
- pause 指标可观测。

---

## Phase 5（16-20 个月）：ZGC 风格并发收集预研与 MVP

### 目标
在不牺牲主线稳定性的前提下，做 ZGC 风格“并发、低停顿”路径。

### 关键任务

1. **并发标记框架**
   - 与 mutator 并发工作；
   - SATB 或增量更新二选一（建议 SATB 起步）。

2. **读/写屏障实验层**
   - 引入可开关屏障策略；
   - 为并发重定位做准备。

3. **着色指针/转发表（简化版）**
   - 先用转发表模拟，避免一开始就侵入对象地址编码。

### 退出标准

- 在 benchmark 场景下停顿明显优于 G1 路径；
- 并发标记正确性通过一致性校验；
- 保持可切换回 G1（双路并存）。

---

## Phase 6（20-24 个月）：JVMTI 设计与实现

### 目标
提供调试/观测能力，支撑后续性能调优与生态工具接入。

### 关键任务

1. **JVMTI 最小子集（MVP）**
   - 线程事件：start/end
   - 类事件：load/prepare
   - 方法事件：entry/exit（可采样）
   - 异常事件：throw/catch

2. **能力协商与回调模型**
   - capability 开关；
   - 事件订阅与低开销快路径。

3. **探针与性能隔离**
   - 非开启模式下几乎零开销；
   - 事件缓存与批量输出。

### 退出标准

- 可通过 JVMTI demo agent 获取关键事件；
- 打开 JVMTI 后性能劣化在可接受区间（先定义基线）。

## 4. 并行工作流（每个 Phase 通用）

每个阶段都执行以下四条并行泳道：

1. **语义实现**：功能代码
2. **验证体系**：单元测试 + 组件测试 + 压测
3. **可观测性**：日志、统计指标、debug dump
4. **文档与规范**：设计文档、运行手册、已知限制

## 8. 风险与应对

1. **过早优化导致复杂度失控**
   - 应对：先语义正确，再做性能；每阶段设“停止线”。

2. **并发与 GC 交叉缺陷难排查**
   - 应对：强制引入 trace id、事件时间线、TSan/故障复现脚本。

3. **目标过大导致交付拖延**
   - 应对：每个 Phase 设 MVP 与扩展层，先交付 MVP。

4. **与 JDK17 差距认知偏差**
   - 应对：维护“兼容性矩阵”文档，明确已支持/未支持语义。

## 11. 扩展路线（Phase 7-10）

本节用于在主线（Phase 0-6）稳定后继续扩展能力。分级定义如下：

- **L1（必须做）**：决定可维护性与正确性上限，应进入正式里程碑。
- **L2（高价值可选）**：显著提升性能或兼容性，建议按资源投入推进。
- **L3（探索项）**：前瞻方向，可并行预研，不阻塞主线交付。

---

## Phase 7（L1）：兼容性矩阵与类库落地（20-28 个月）

### 目标
把“对标 JDK17”从口头目标变成可追踪、可验收的兼容性数据体系。

### 关键任务

1. **建立 JVM 兼容矩阵**
   - 维度：classfile version、字节码指令、异常语义、并发语义、反射/JNI/JVMTI 子集。
   - 输出：`docs/compatibility/JDK17_COMPAT_MATRIX.md`（状态：支持/部分支持/不支持/计划中）。

2. **标准类库最小可运行子集**
   - 明确 `java.lang`, `java.util` 的优先级 API 子集。
   - 先围绕“可运行真实小程序”构建，不追求全覆盖。

3. **真实工作负载验证**
   - 选 3-5 个样例项目作为兼容基准（CLI 工具、集合操作、并发基础用例）。
   - 建立 nightly compatibility 回归任务。

### 退出标准

- 兼容矩阵持续更新且与 CI 结果一致；
- 至少 3 个真实样例稳定运行；
- 每次版本发布附兼容性变化说明。

---

## Phase 8（L2）：性能工程体系与最小 JIT 路线（24-32 个月）

### 目标
建立可量化的性能闭环，避免“优化靠体感”。

### 关键任务

1. **基准测试体系**
   - 指标：启动时延、吞吐、GC 停顿、峰值内存、CPU 占用。
   - 产出：benchmark harness + 历史趋势图（至少按周）。

2. **热点探测与解释器优化**
   - 方法调用计数、回边计数；
   - 可选模板解释优化（dispatch 优化、热点路径内联式处理）。

3. **最小 JIT 预研（可开关）**
   - 先做“热方法识别 + stub 编译”；
   - 保持可回退解释执行（双路切换）。

### 退出标准

- 主 benchmark 集合有稳定基线；
- 每次性能回归可自动告警；
- 至少一个热点场景吞吐提升可量化。

---

## Phase 9（L2）：JMM 子集与高级并发语义（28-36 个月）

### 目标
从“线程能跑”升级到“并发语义可靠”，对齐 JDK17 核心内存模型预期。

### 关键任务

1. **JMM 子集定义**
   - 明确 `volatile`、final 字段发布、synchronized 的 happens-before 边界。
   - 文档化“当前保证”与“未保证项”。

2. **并发语义测试集**
   - 引入 litmus tests（重排序、可见性、竞态边界）。
   - 多平台跑一致性验证。

3. **并发容器与 API 对照验证**
   - 选取 `java.util.concurrent` 子集用例验证语义。

### 退出标准

- JMM 子集有正式规范文档；
- 并发语义测试可重复、可回归；
- 关键可见性问题有明确判定与修复路径。

---

## Phase 10（L3）：运维诊断与生态工具链（并行长期）

### 目标
把 JVM 从“开发可用”升级到“可运维、可诊断、可接入工具生态”。

### 关键任务

1. **诊断工具最小集合**
   - `jstack` 风格线程 dump；
   - `jmap` 风格堆摘要；
   - `jcmd` 风格运行时命令入口。

2. **故障注入与混沌测试**
   - GC 压力、类加载失败、锁竞争极端场景注入；
   - 自动化复现脚本与失败档案归档。

3. **安全与验证增强**
   - 字节码验证器（verifier）逐步落地；
   - native 接口边界检查与最小沙箱策略。

### 退出标准

- 线上问题可通过诊断命令定位到模块级；
- 有标准化故障演练与复盘模板；
- 高风险输入路径具备基本防护。
